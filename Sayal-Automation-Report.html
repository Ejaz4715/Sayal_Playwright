Reading the eight expected failures

Each guard asserts the behaviour the product should have and is marked test.fail(). While the defect stands, Playwright reports it as an expected failure — visible in every run, never counted as a pass. The day a defect is fixed, its guard becomes an unexpected pass and the suite turns red until someone removes the marker. No assertion was weakened to make a guard go green.

Section 02

Execution order is a safety mechanism

The four projects run strictly in sequence, enforced by dependencies in the config. The order is not cosmetic: Sayal rate-limits login attempts rather than failures and answers 429 SE0053 with a roughly ten-minute block that refuses correct credentials too. Signing out also invalidates the shared token server-side. Running these stages in any other order starves the functional suite and reads, from the outside, exactly like an environment outage.

Also worth knowing

Pre-production serves a static CAPTCHA image that always reads 12345 (ISS-21), which is what makes automated login possible here at all. Server error codes such as SE0011 and SE0053 are surfaced to users verbatim (ISS-07); the negative-auth tests assert on those codes because that is what the product returns.

Section 05

Three environment facts encoded in the framework

Each of these caused a real failure before it was understood, and each is now handled in the configuration rather than left as tribal knowledge. Anyone picking up the suite should read them before diagnosing a red run.

The host resolves only on the corporate network

pre-sayal.housingapps.sa is served by split-horizon DNS and answers 10.200.1.206 internally. Public resolvers return NXDOMAIN by design. A DNS failure means you are off the VPN, not that the environment is down — an earlier pass concluded the record had been withdrawn and lost two days to it.

Login attempts are rate-limited, not just failures

After roughly a handful of attempts the account is blocked for about ten minutes and refuses correct credentials. Hence one login per run, retries disabled, and the project ordering in Section 02. The login helper names a 429 SE0053 rejection explicitly rather than letting it surface as a navigation timeout.

HTTP/2 is broken on this host

Chromium runs with --disable-http2. On the default path, Next.js chunks fail with ERR_HTTP2_PROTOCOL_ERROR and the post-login redirect never completes — which previously looked like an application bug and is not one.

Two further product traits shape every locator: the admin list screens expose no headings and no ARIA roles, so readiness anchors on the grid container; and the SPA's load event never settles, so navigation uses waitUntil: 'commit' and networkidle is never used as a readiness strategy.

Section 06

Data safety

The suite is read-only against shared pre-production data. This is a design constraint, not a limitation to be lifted casually — the records it reads are real, and several of the state transitions it declines to exercise cannot be undone in this environment.

  • No test creates, edits, deletes or transitions a real record. The eight admin lists, the client and request detail pages and all seven channel forms are opened and inspected, never submitted.
  • Where a write path must be exercised to prove a defect (ISS-38, ISS-39), the request is intercepted with page.route and aborted before it leaves the browser. The attempt is recorded; nothing is stored.
  • Shared records used as fixtures are listed explicitly as read-only: one client, one request per status found by scanning all 261 standard requests, one deactivated user, and one public quotation token.
  • Data the suite generates is recognisable — AUTO_SAYAL_<timestamp> values used by the no-match search cases, which query rather than write.

Section 07

Deliberately not automated

Stated plainly so the coverage above is not read as more than it is. Each of these is blocked by a specific missing capability, not by effort, and each becomes automatable the moment that capability exists.

  • Request state transitions — accept, reject, approve, cancel, schedule. They cannot be undone in this environment. What is asserted is which actions the product offers at each of the seven statuses, which is the testable half of the gating rule.
  • Quotation creation — same reason. The suite verifies that the control appears exactly where it should (on an accepted request) and nowhere else.
  • Channel form submission — a saved channel attaches to a shared request and cannot be removed cleanly, so empty-submit validation is asserted from the form's own required markers rather than by posting.
  • Account lockout (AUTH-012 / AUTH-013) — verifying a lockout means causing one, and there is no disposable account to cause it on. These stay manual until one exists.
  • Unblocking all of the above requires a disposable client, a disposable campaign request and a second login account in pre-production. That is the single highest-value thing that could be added to this environment.

Artifacts and reproduction

What this run left behind

playwright-report/index.html — the full interactive HTML report, self-contained, with the eight attachment files under playwright-report/data/. test-results/results.json holds the machine-readable record every figure in this report is drawn from, and test-results/.last-run.json the run verdict. Each guard also wrote an error-context.md ARIA snapshot of the page at the moment its assertion failed.

No traces, videos or screenshots

Capture is set to retain-on-failure, and an expected failure is not a failure — so the eight guards produced context snapshots but no trace or video. That is correct behaviour, and it is also why an unexpected failure in a future run will arrive with a full trace attached.

Reproducing it

npm install, npx playwright install chromium, then npm test from the corporate network. npm run report opens the last HTML report. Scope re-runs with --project=sayal to spend no login attempts; leave about ten minutes between full runs.
